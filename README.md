## 项目简介

面向 **Linux 服务器 / 嵌入式板卡** 的运维诊断场景：从真实日志与系统快照取证，经图编排与人机确认，产出**可追溯**的诊断报告。

**设计立场** —— 让程序拿确定性、让模型做归因、让副作用必须人批：健康日志不惊动模型（0 次调用收工），异常才升级到 LLM；任何写操作都停在 `interrupt()` 等人点头。

## 亮点速览

- **程序算确定性、模型做归因** —— 网关判据、工具选择、循环上限、停止条件全在代码里；健康日志 **0 次 LLM 调用**收工
- **图编排 + 运行时动态并行** —— LangGraph StateGraph，`Send` 扇出 N 路取证，框架 barrier 自动汇总
- **副作用必须人批准** —— `interrupt()` 让审批发生在流程中段；`SqliteSaver` 支持**跨进程断点续跑**
- **工具通道可换** —— 同一张图，`--tools direct|mcp` 在「同进程函数调用」与「MCP 协议（7 工具）」之间切换
- **三层判据评测** —— 黄金集 8 条（含负向断言与失败路径）实测 **9/9**；指纹缓存 + 模型分级使单次调用省 **57%** token
- **工程化闭环** —— 运行时预算刹车、告警收敛（14 条发现 → 9 个事件）、安全审计（哈希链）、**18 步 CI 门禁（420+ 项测试）**

## 一、架构（`--graph` 实测打印出来的图）

```
__start__ --> scan（程序网关：数 ERROR 行数，0 次 LLM）
scan -. 有异常 .-> plan（模型拆子任务）
scan -. 无异常 .-> __end__            ← 明显没事时，成本为零
plan -. Send 动态并行 .-> investigate × N（程序取证 + 模型归纳）
investigate --> confirm               ← 框架自带 barrier：全部完成才汇总
confirm -. 人批准了 .-> report --> __end__
confirm -. 一个都没批 .-> __end__     ← 人的决定真的能改变走向
```

三条设计原则（都有实测数据支撑，详见笔记）：

1. **该由程序拿的确定性，一步都不让给模型** —— 网关判据、工具选择、循环上限、停止条件全在代码里
2. **工具与编排解耦** —— 同一张图，工具通道可换：同进程函数调用 / MCP 协议（`--tools direct|mcp`）
3. **副作用必须人批** —— `interrupt()` 让图停在半路等人；报告分「已获批执行 / 尚未获批执行」两栏

## 六、可观测性（追踪）

**状态 ≠ 过程**：checkpointer 回答"图停在哪、能不能续跑"；trace 回答"这段时间花了多少、慢在哪一步"。

- 追踪是**插座**：本地 JSONL（默认，永远可用）/ Langfuse（配了 key 才启用）/ 关闭（`--no-trace`）
- 埋点**不侵入业务**：`traced_node()` 在 `add_node` 处包装，节点体一个字不用改
- 跨进程也能拼成一条链：**run 边界 = 进程边界**，同一个 trace 下多个 run

```powershell
& $py day36_graph_mcp.py --trace-report trace-hitl     # 读 traces/trace-hitl.jsonl 出报告
```

实测一份报告（跨进程续跑，全文见 `追踪与可观测性笔记_2026-09-22.md`）：

| 项 | 数值 |
|---|---|
| 覆盖 | **2 个进程 run**（42.5s + 3.7s），48 条记录 |
| LLM | 6 次，合计 73.7s，**token 输入 1313 / 输出 1690** |
| 工具 | 5 次（MCP），合计 90 ms，平均 17.9 ms/次 |
| 结论 | **优化要打在 LLM 那一侧**（工具通道差三个数量级）|

要真上 Langfuse：`uv pip install langfuse` + 往 `.env` 加 `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY`
→ 同一条命令自动改走上报，**代码不用动**。（注意 langfuse 已到 v4，是 OTEL 架构，
v3 的 `start_as_current_span` 已不存在；且**没有服务端时不要启用**，退出会白等导出超时。）

## 七、评测（`eval_agent.py`）

**Agent 评测和 LLM 评测不是一个难度**：路径不唯一（换个走法就红）、答案是自由文本、还带工具副作用。
所以判据分三层，且**能程序判的一律不给模型判**：

| 层 | 判什么 | 花钱吗 |
|---|---|---|
| **L1 确定性** | 网关判定 / fixture 可读性 / 路径拒绝 / 判据表自洽 | 不花（秒级）|
| **L2 客观文本断言** | **必须出现**（客观特征：`5432`/`No space left`）与 **必须不出现** | 花 |
| **L3 过程与成本** | 调用次数 / token / 耗时 / 是否触发人机确认 / 是否超预算 | 花 |

8 条黄金集（`--offline` 可免费验判据表）：

| 用例 | 判据要点 |
|---|---|
| G01 双故障域 | 两组并发故障都要指出 |
| G02 只问磁盘 | 限定视角后仍要给出磁盘结论 |
| G03 健康日志 | **网关 0 次 LLM 收工**，且不许编出报告 |
| G04 只有 DB 故障 | ★负向：该日志磁盘健康，**不许出现磁盘告警字样** |
| G05 只有磁盘故障 | ★负向：该日志 DB 健康，**不许出现 `5432`/拒绝** |
| G06 不许无中生有 | ★日志里没有 OOM/段错误，出现相关**断言**即判挂 |
| G07 读不到的日志 | **读不到 ≠ 没有异常**：必须显式失败 |
| G08 越界路径 | ★安全：拦住 `../.env`，且输出里不许出现 `sk-` |

```powershell
& $py eval_agent.py --offline          # L1，秒级，先跑这个
& $py eval_agent.py                     # 全量（--tools mcp）
& $py eval_agent.py --tools direct      # 换通道再跑（结论应当一致）
& $py eval_agent.py --only G01,G04 --runs 2   # 小样 + 稳定性
```

**第一次跑的结果：8/8 通过，30 次 LLM 调用、15913 token。**
但更值钱的是过程里抓到的两件事：

1. **评测先抓出的是「判据自己的 bug」**：G04 首跑判挂，报告里明明写了"DB 连接拒绝 / PostgreSQL 不可达"——
   是我的备选词写窄了（只写"连接被拒/数据库"），**把模型冤枉了**。
   假阴性比漏判危险：你会去修一个没坏的东西。**所以失败样本一定要人工看一眼**。
2. **顺手补了一个真 bug**：工具失败原来会把异常抛出去、图当场崩（Day 32 坑表 #11 没落到图上）。
   现在统一转成带信息的结果字符串，`scan` 区分「读不到」与「没有异常」（G07/G08 就是守这条的回归用例）。

## 八、运行时预算（刹车）

**成本不是口号，是四条硬上限**：LLM 调用次数 / token / 工具调用次数 / 墙钟。用尽时**不崩**，
而是拿 checkpointer 里的已有证据出一份**降级报告**（程序模板生成，**刹车后不再调用模型**）。

```powershell
& $py day36_graph_mcp.py --max-calls 4                  # 4 次调用后刹车 → 降级报告
& $py day36_graph_mcp.py --max-seconds 30               # 墙钟刹车（同时是单次调用的超时上限）
& $py day36_graph_mcp.py --max-tokens 8000 --max-tools 6
& $py test_budget.py                                    # 26 项离线测试，0.2s，不花钱
```

三条设计要点（都有实测支撑）：

1. **刹车要能"拒"，也要能"截"**：只在调用之间检查计数，最坏超一整次调用（实测单次 LLM 9.7s ↔ 99.9s）。
   所以"剩余预算"会作为**单次调用的超时上限**交给 HTTP 客户端，异常分两类：
   `BudgetExceeded`（拒下一单）与 `CallTimeout`（截断在途的一单）
2. **重试必须记账**：openai SDK 默认重试 2 次且**不经过我们的账本**（实测给 5.9s 超时、实际 21.3s）
   → `max_retries=0`，重试自己写，**每次重试重新占一个名额**
3. **并发下该共享的必须加锁**：预算是全流程共享的一条账（与 Day 37 那个必须**隔离**的 span 栈相反），
   用"预留-结算"并在**同一把锁**里 check + 加；取消/异常时用 `try/finally` **无条件释放**

## 九、本地 CI（回归门禁）

**口头约定"记得跑测试"等于没有约定** —— 所以把免费档挂到了 git pre-commit 上，让机器回答"能不能提交"。

| 档 | 内容 | 成本 | 实测 |
|---|---|---|---|
| **L1**（默认，钩子自动跑）| **敏感文件不进暂存区** / **门禁不依赖控制台编码** / 语法编译 / 图能搭起来 / 预算 26 项 / 真机取证与规则 51 项 / 沙箱边界 21 项 / 趋势预测 25 项 / 成本控制 46 项 / 告警收敛 112 项 / 因果图自检 / 误报反馈与抑制 64 项 / 抑制规则自检 / **安全审计 51 项** / **审计哈希链自检** / **MCP server 能导入且工具齐全** / 评测 L1 自检 / 工具层回归 24 项 | 免费、不要 key | **18 步 26.8s**（累计 420 项测试）|
| **L2**（`--tier l2`）| 在线评测（默认只跑 `G03,G07,G09` 便宜用例）| 花小钱 | 19 步 34.4s+（在线 3/3、7.2s）|

★ **门禁最大的坑不是它报错，是它不报错**：`server.py` 里有行 `print(..., file=sys.stderr)` 用了 `sys`
但文件里没 `import sys` —— **MCP server 因此死了 4 个提交，而门禁 15 步一直放行**，
因为**没有任何一步 import `server.py`**（测的是被它 import 的 day32 工具层）。
➡️ 教训：**测试没覆盖的东西等于不存在**。现在有一道
`import server` 并列 7 个工具的门禁，import 期就崩的错再也藏不住。

⚠️ **门禁的结果不允许取决于环境变量**（实测踩到）：手动跑全绿、`git commit` 触发钩子时 5 步失败 ——
根因是子进程按 Windows 控制台代码页（cp936）输出、而 `ci.py` 按 UTF-8 解码，
`✓/✗` 不在 GBK 里会直接抛 `UnicodeEncodeError`。现在 `ci.py` **给所有子进程固定 UTF-8**，
并新增一道自检：让子进程输出 `✓` 并匹配它 —— 只有真的固定了才过。


## 十一、真机运维入口（`day42_live.py` + `collect.py`）

**两个入口，两种活**：`day36_graph_mcp.py` 面向**日志诊断**；`day42_live.py` 面向**主机体检**（能真跑在你的机器/板子上）。

```powershell

& $py test_collect.py                     # 35 项离线测试，0.1s
```

**12 条确定性规则**（程序判，0 次模型调用）：磁盘用量 / **inode** / MemAvailable（不是 MemFree）/
swap / 负载（跟核数一起看）/ **OOM kill 计数**（`/proc/vmstat`，日志里只看得到"进程没了"）/
fd 用量 / TIME_WAIT / **PSI 压力** / **cgroup 限额**（主机充足但容器先被 OOM）/ **温度**（嵌入式头等）/
大文件（谁把盘吃满）。

三条工程底线：

1. **只读**：不起 shell、不写文件 —— 测试里断言"采集前后目录内容一致"
2. ⚠️ **缺数据就说缺**：Windows 上没有 `/proc` → 该维度标 `available:false`，**规则绝不触发**
   （运维工具最危险的失败是"没看到就报健康"，与 Day 38 的"读不到 ≠ 没有异常"同源）
3. **采集自身有上限**：读文件 256KB、遍历 20000 条/深度 3、权限失败静默跳过；失败降级不抛

**可用性**：退出码 `0=ok / 1=warning / 2=critical` + `--json` 结构化输出 → 直接当监控插件；
模型只做**归因与排序**，prompt 里硬约束"不许引入规则未发现的严重项，猜测必须标注"。

### 趋势与预测（`trend.py`）：把"当前值"升级成"可行动的时间预算"

```powershell
& $py day42_live.py                                  # 每次体检自动写历史（snapshots/history.jsonl）
& $py day42_live.py --trend                          # 打印趋势详情（含"为什么没给预测"）
& $py day42_live.py --no-history                     # 一次性检查，不留痕
& $py test_trend.py                                  # 25 项离线测试，0.1s
```

**为什么这是最有价值的一半**："磁盘 91%，warning" 这种告警值班的人看一眼就放到明天；
"**按当前速度 53 分钟后到 95%**" 才逼人现在动手。实测输出：

```
[critical] INODE_FILL_FORECAST · /：按当前速度（+2.25 点/小时，R²=1.0，11 点/240 分钟）
           预计 53 分钟后达到 95%（现值 93.0%）
[critical] DISK_FILL_FORECAST · /var：预计 60 分钟后到 95%（现值 92.0%）
[critical] THERMAL_RISING · SoC：预计 53 分钟后到 85°C（现值 82.3°C）
```

**四条纪律**：
1. ⚠️ **样本不够就不给预测**（n≥3、跨度 ≥10 分钟、窗口内变化 ≥1 点）—— 宁可说"不知道"，
   也不拿两个点连条线当趋势。**运维工具最贵的错是让人信了一个编出来的数**
2. **预测带可信度**：斜率 / R² / 窗口区间 / 样本数都给出来，值班的人自己判断
3. **历史只存要算趋势的指标**（不存整份快照），每主机裁剪到 500 条
   —— **历史无界增长本身就是个运维问题**（被自己的监控吃满磁盘）
4. **已超阈值的不重复预报**（现状规则已报过）—— 重复告警是让人关掉告警的第一步

★ **预测也驱动退出码** —— 监控因此能**提前**报警，而不是等阈值被击穿。

### 成本控制（`cost.py`）：监控是**反复跑**的，所以"单次便宜"不够

```powershell
& $py day42_live.py --quiet-if-ok              # cron 模式：健康时只打一行
& $py day42_live.py --hourly-token-limit 200000   # 每小时 token 限额，超了只出规则结论
& $py day42_live.py --price-in 1 --price-out 2    # 想算钱自己给单价（默认只报 token）
& $py test_cost.py                             # 33 项离线测试，2.2s
```

三件套：**① 归因缓存**（状态不变 → 0 次调用）｜**② 模型分级**（无发现不调；仅 warning 用便宜档；
critical 或发现 ≥5 用强档）｜**③ 跨运行账本 + 小时限额刹车**（超了不偷偷花钱）

**实测（同状态连跑两次）**：

| 轮次 | 模型调用 | token | 用时 |
|---|---|---|---|
| 第 1 次 | 1 | 960 | 4.2s |
| **第 2 次（缓存命中）** | **0** | **0** | **0.1s** ⇒ 延迟降 42 倍，成本归零 |

⚠️ **实现缓存时踩到的真问题**：第一版**永远命不中** —— 指纹里放原始数字，而可用内存每次抖动
（13.2% → 12.8%）。正解：**只对百分比按桶量化**（5 个点一桶），**IP/端口/计数保持精确**。
➡️ **抗抖动，但不掩盖实质变化**（跨桶必失效，TTL 是第二道保险）。

⚠️ **不内置价格**：模型价格随时变，编一个"每百万 token X 元"就是骗人 —— 只报 token，
要算钱自己传 `--price-in/--price-out`。

### 告警收敛（`converge.py`）：一次故障 N 条告警 → **一个事件 + 根因/连带**

企业调研里排第一的痛点不是"没有告警"，是**一次故障几十条告警、真信号被噪声埋掉**。
收敛把「规则发现」聚合成「事件」，`14 条发现 → 9 个事件`、`14 个待批动作 → 9 个`。

```
【告警收敛】14 条发现 → 9 个事件（压缩 1.56×）｜断言根因 1｜并列/同源 2｜跨事件弱关联 10

  [critical] EVT-1 · 内存不足（引发 3 项连带）
      资源：主机内存、内核｜规则：MEM_AVAILABLE_LOW, OOM_KILL_EVENTS, PSI_MEM_PRESSURE, SWAP_PRESSURE
      ▸ 根因（已断言）：MEM_AVAILABLE_LOW（linux-dump/meminfo）可用内存仅 4.4%（167.4 MB / 3802 MB）
      ▸ 连带 3 项（跟着根因一起消，别单独处理）：
          · OOM_KILL_EVENTS｜kernel：vmstat 记录 oom_kill=3 次   ← MEM_AVAILABLE_LOW[必然]
          · PSI_MEM_PRESSURE｜PSI memory：avg60=28.44%   ← MEM_AVAILABLE_LOW[必然]
          · SWAP_PRESSURE｜swap：swap 已用 78%   ← MEM_AVAILABLE_LOW[必然]
      ↔ 与 EVT-2 可能相关：EVT-2 里的 CGROUP_MEM_NEAR_LIMIT 可能解释了本事件的 OOM_KILL_EVENTS
        （**未断言**）：容器限额触顶会被 cgroup 杀；但 vmstat 的 oom_kill 不区分主机级还是 cgroup 级
      ▸ 先做：找内存大户并限制；确认是否已在换页（性能会断崖式下降）
```

**四条不让步的设计**（每条都对应一个"看起来更聪明但更坏"的做法）：
1. **因果由代码判定，不由模型判定**：因果边是写死的领域知识表（9 条边，每条带强度与文字理由），
   `day42_live.py --explain-graph` 可打给人审 —— **人可以质疑和推翻我们的图**，这比"AI 说的"更值得信任
2. **分强弱，弱因果不许断言根因**：`strong`（内存耗尽→OOM killer）才写"根因"；
   `plausible`（大文件→盘满）只给**候选**，并且能核验的就核验成事实（「已核验占比 21.0%」）
3. **收敛不能吃掉告警**：不变量 `sum(事件成员) == len(发现)` 同时进测试与运行时自检
   （收敛工具最经典的失败就是"顺手过滤掉了不想看的发现"）
4. **不许把"空间相邻"当因果**：同一挂载点的**空间满与 inode 满互不解释**（大文件不吃 inode），
   写成反例表 `NON_CAUSAL_NOTES` 并进测试；事件里**连带**（跟着根因消）与**并列**（要分别处理）分开列

**因果图自检进 CI**：`converge.py --check-graph` 检查无环 / 规则齐全 / 反例表不自相矛盾 ——
**图错了归因就是错的**。测试 `test_converge.py` 112 项钉住完整性、防过度合并、不编根因、收敛必须真变短。

**喂模型用事件表（`--llm-input events`，默认）**：因果已由程序判定，模型只做措辞与优先级，
不需要（也不该）自己推理因果。实测输入 token `1202 → 944`（真实 API：`1433 → 1245`）。

**诚实边界**：本收敛是**单机单次快照内**的；跨机时序聚类需要中心侧带时间戳的告警流（未接，不假装有）——
`fleet_cluster()` 只给"同一批巡检窗口内同一规则多台触发 → **共性嫌疑**"的近似，并明说没有跨机时钟对齐。
另外**根因可能已从快照里消失**（OOM 杀进程后内存恢复），所以收敛不要求根因当前可见，事件会写明。

### 输出上限与"白烧"记账（成本控制的正确性）

★ 两个实测教训（比优化本身更值钱）：

**① 账本不许漏记成本。** 推理型模型在 `max_tokens` 偏小时会**把预算烧在推理上、正文为空** →
自动放大重试（`context.make_llm` 的空正文守卫），**废掉的那 2000 token 是真花钱的**。
原来只取 `usage_sink[-1]`（成功那次）→ 漏记。现在 `cost.summarize_usage()` 按**每次尝试**累加，
并单独标出白烧量；账本能回答"**有多少 token 是白烧的**"（`retry_runs_today` / `wasted_tokens_today`）。

**② 输出上限不是越大越好**（真实 API，同一提示词，各 3~4 次）：

| 上限 | 平均 token/次 | 重试率 | 平均耗时 |
|---|---|---|---|
| 2000 | 6409 | 3/4 | 19.4s |
| **3000（默认）** | **5443** | **2/4** | **15.8s** |
| 4000 | 6171 | 1/3 | —（失败那次白烧 4000、36s） |

推理 token 是**弹性**的：`cap=2000 → 推理 1118 字/正文 583 字`，`cap=4000 → 推理 4131 字/正文 445 字`
（**给得越大想得越久、正文反而更短**），而失败一次的浪费 = 该上限本身。默认改 3000 后实测**一次成功**：
`3204 token / 无白烧` vs 旧默认 `7421 token / 白烧 2000` → **省 57%，延迟 20s→10s**。

反直觉的一条：想把输出限死（"只输出编号列表、每行≤45字"）反而让推理暴涨到 3163~9200 字、整次调用失败 ——
**"要求更短"不等于"更便宜"**。任何省钱的提示词改动都必须用真实 API 量过才算数。

### 误报反馈与抑制（`feedback.py`）：让工具**能被纠正**，但绝不顺手压掉真问题

企业调研里"反馈闭环"那条的原文很难听但很准：**误报没人标记、工单随手关 → 不会越用越准，只会越用越吵**。
一个只会告警、不会**被纠正**的工具在真实运维里活不过一个月 —— 值班的人的理性反应是
**先静音，然后漏掉真故障**。所以"能抑制"是必需的；但"能抑制"和"乱抑制"只差一条线，跨过去的代价是**漏掉真故障**。

```
【已抑制】1 条（占总发现 7%） —— 抑制**不等于删除**：这些仍在报告里，只是不进退出码
  · warning TCP_TIME_WAIT_HIGH @ net/tcp：TIME_WAIT 连接 7213 条
      被 SUP-8f96fe2b64 压住（exact）｜原因：板子跑 MQTT 长连接池…｜到期：2026-09-29…｜天花板：warning
```

**七条纪律**（每条都对应一个"看起来更省事但更坏"的做法）：

| 纪律 | 更省事但更坏的做法 → 后果 |
|---|---|
| **① 抑制不是删除**：被压住的发现照旧打印，写明被谁压住/为什么/何时到期 | 压掉就当没看见 → 出事时无法回答「**当时为什么没报**」（复盘问的第一个问题）|
| **② 严重度天花板**：标了"92% 正常"就只压这条 warning，涨到 97% **照样报** | 按对象压 → 容量规划变了、盘真满了，你什么都不知道 |
| **③ 默认 7 天过期**（`hours` 有上下界，传 0 直接拒绝）| 永久抑制 → 半年后没人知道它为什么存在，而它正在安静吃掉告警 |
| **④ 理由必填、撤销也要理由、`sup_id` 确定性**（`sha1(host\|rule\|subject\|match)`）| 自增序号 → 规则重建后序号变，**撤销会撤到别的规则上、把真故障放回来** |
| **⑤ 范围越宽要的证据越多**：`exact` 1 个标记；`prefix`/`rule` 必须 `--wide` **且 ≥2 个** | 默认给最宽匹配 → 一周后你的告警全哑了 |
| **⑥ 过宽/失效要从数据里看出来**：跨运行命中计数 + 健康检查 | 不看数据 → 一条能吃掉所有磁盘告警的规则"看起来很干净" |
| **⑦ 不许让模型决定抑制**：只来自人的显式标记；模型仅被**告知**"另有 N 条已人工确认是误报" | 让模型顺手压 → 不可审计，且它会压掉真问题 |

**数据分层**：`feedback.jsonl`（**只追加的人为事实**）→ 派生抑制规则 → `suppression_state.json`（命中计数）。
**事实只追加、结论可重算** —— 撤销不用改写历史，审计链永远完整。

**阈值建议**（比逐个压制更好的那条路）：同一规则在 ≥3 个**不同对象**上被标误报
→ 建议「**先调阈值**，而不是给每个对象各加一条规则」（逐个压制是把一个系统性误报拆成 N 条没人看得懂的规则）。

**实测**（真实 fixture）：基线 `14 条/9 事件/退出码 2` → 标记一条误报后 `14 条（1 条抑制）/8 事件`。
另造只含一条 warning 的快照证明**抑制真的能改变退出码**：`warning→退出码 1` ⇒ 标记后 `ok→退出码 0`，
且**发现仍在「已抑制」区**。➡️ **退出码听人的，告警记录不听人的**。
标记 `critical` 误报时运行时当场点名「**天花板是 critical** —— 它会压住最严重的那一档」。

**跑法**：

### 安全审计 + 工具级作用域（`audit.py`）：MCP server 是**信任边界**

企业调研对 MCP 的原话：**MCP server 是新的信任边界，不是协议适配器** —— 要**工具级 Read/Write/Admin 作用域**
（不是服务级白名单）+ 结构化审计日志。一个"能给模型读日志"的服务，本质是**一个能读你磁盘的远程入口**；
出事要能回答：**谁、在什么时候、读了什么**。

```
【审计报告】记录 3 条（校验 3 条）｜主体 local-os-user（未认证）｜传输 stdio
  哈希链校验：✅ 完整（无改动痕迹）
  按工具：list_files×1、read_log×1、live_diagnose×1
  ⚠ 触碰敏感名的尝试：1 条
    ! 2026-09-22 20:41:04 read_log → .env（被沙箱拒绝）
    #1 list_files（read）OK｜14 字符        ← **只记形状，不记内容**
    #2 read_log（read）FAIL｜ValueError: 文件名命中敏感清单：.env
    #3 live_diagnose（read）OK｜发现 14 条（抑制 0 条）
```

| 纪律 | 为什么 |
|---|---|
| **作用域按「工具」声明且 fail-closed**：`tool_scopes.get(tool, "admin")` | 服务级白名单粒度太粗（里面多一个能删文件的工具照样放行）；**忘记声明的新工具 = 被拒绝 + 被审计**，而不是"没写就随便放" |
| **记「读了什么」，绝不记「读到了什么」** | 日志正文可能是密码/客户数据；抄进审计文件 = 审计日志自己成了新的泄露面。只记字符数/行数/是否含错误关键词 |
| **哈希链**（`prev`/`h`）：改内容/删除/换序都能指到第几条 | ⚠ 诚实边界：**这不是防篡改**，只让篡改可被发现（能整份重写的人也能重算链） |
| **拒绝也要审计**（最有价值的部分）| 只记成功调用的审计日志几乎没价值；越界尝试才是要看的 |
| **有上限会轮转**（5MB/保留 5 个，链跨轮转不断）| 把磁盘吃满的审计日志是另一种事故 |
| **身份诚实**：`principal = 本地 OS 用户（未认证）` | stdio **没有认证**，不假装成已认证主体（真认证是 P2 的 HTTP + OAuth2.1/PKCE）|

**两道闸门各管一件事**（实测 `read_log('.env')` 是被**沙箱**拦下的，不是作用域）：
作用域闸门答"**有没有资格调这类工具**"，沙箱闸门答"**这个具体路径能不能碰**" ——
**"允许调 `read_log`" ≠ "允许读 `.env`"**，两次判定都进审计。

```bash
python audit.py --report              # 谁/工具/拒绝/触碰敏感名的尝试
python audit.py --verify              # 校验哈希链（改内容/删除/换序都会断链）
python audit.py --self-test           # 演示 fail-closed：未声明作用域的工具被默认拒绝
DIAG_SCOPES=read python server.py     # 作用域可用环境变量配（默认只有 read）
```

⚠ **审计默认不许关**（`--no-audit` 只在离线复现时用）；关掉时返回值里会标明 `skipped`，
调用方必须知道"审计没生效"，而不是以为记上了。

### 沙箱根可配置（`--root` / `DIAG_ROOT`）+ 三道安全边界
读真实 `/var/log` 需要它。**根可配 = 攻击面可配**，所以同时加了：
① **文件名黑名单**（根内也拒：`.env`/`*.pem`/`id_rsa*`/`*.sqlite`/`*secret*`）；
② **危险根拒绝**（`E:\`、家目录 —— 等于没有沙箱）；③ 根里含密钥时**告警**（MCP server 写 stderr 审计）。
`test_sandbox.py` 21 项钉住这些行为。

**边界（刻意的）**：只给建议**不执行**任何处置；执行层（Ansible/SSH/运维平台）自己做二次校验与审计。

## 十二、已知局限（如实列，不粉饰）

1. **日志是 fixture，不是真机**：真要上生产得换 `journalctl` / `df -h` / `dmesg` 采集
2. **结论措辞受编排影响**：同一份日志，图版说"磁盘主因"、`create_agent` 版说"DB 主因" —— 报告里的"根因"是编排的产物，**不能当客观事实**（笔记里有三次复现）
3. **预算只限轮数**：总调用数 / 总 token / 墙钟超时还没做（Day 32 遗留）
4. **工具只读**：写类动作（清日志、重启）目前**只出建议不执行** —— 等 guardrails 做完再放开
5. **两套解释器**：是隔离的代价，换机器要重装（README 已写清）
6. **L2 在线测试要 key**：模型行为类断言在 CI 里会跳过
